# 架构：可复用的制度问答 RAG 框架

> 这份文档描述「目标架构」而不只是现状，并标注每一步的落地状态。
> 目标：把 PolicyRAG 里与「制度/政策」无关的部分抽成通用能力，换一个垂直领域
> （合同、工单、手册、法规）只写一个**领域包**，不改核心代码。

## 1. 分层

```
┌──────────────────────────────────────────────────────────┐
│ 接口层  app/api        HTTP/SSE 适配：参数校验、错误码、流式  │
├──────────────────────────────────────────────────────────┤
│ 应用层  app/qa         AnswerFlow：路由→改写→检索→提示→生成  │
│         app/ingest     Pipeline：解析→结构化→质检→发布        │
├──────────────────────────────────────────────────────────┤
│ 核心契约 app/core/contracts.py  Protocol 与数据类            │
├──────────────────────────────────────────────────────────┤
│ 适配器  app/retrieval  app/llm  app/store  app/domain       │
│         （BGE/BM25/Chroma、OpenAI 兼容客户端、SQLite/文件）  │
└──────────────────────────────────────────────────────────┘
```

依赖方向只能向下：接口层 → 应用层 → 契约；适配器实现契约，彼此不反向依赖。
`app/wiring.py` 是唯一的组合根（允许跨层拼装），其余模块不得 import 上层。
这两条规则由 `tests/test_architecture.py` 自动检查。
`app/domain`（领域包）只被应用层与适配器**显式**引用，核心契约里不出现任何
「制度」「条款」「废止」字样。

## 3. 六条设计原则

1. **契约先行**：跨层只认 `app/core/contracts.py` 的方法签名与字段；
   换实现不改调用方。测试里的假编码器/假模型就是按契约写的。
2. **领域包隔离**：制度专属概念（状态词、版本号、条款号、提示词口吻）只出现在
   `app/domain/` 与 `app/llm/prompts.py`。核心层出现「制度/条款/废止」等字样即视为缺陷。
3. **显式流水线**：入库与问答都是「阶段列表」，每阶段输入输出可打印、可单测、
   可在配置里增删，而不是一坨函数互相调用。
4. **发布是不可变产物**：一次发布 = 一个目录 + `manifest.json`；线上只通过
   `active_release.json` 原子切换，回滚 = 改指针。向量、单元、片段同目录同版本号。
5. **失败可解释**：检索为空、低相关、旧版本、拒答都要给出结构化 `notes`，
   UI 与评测都读同一份诊断信息。
6. **可替换件清单要短**：编码器、向量索引、词法索引、生成模型、解析器、元数据库，
   六个替换点足够了；再多就是抽象泄漏。

## 4. 数据契约（对下游稳定）

- `unit`（单元 = 一条可引用的最小制度条文/段落）
  `unit_id, doc_id, doc_title, doc_number, unit_type, article_no, heading_path[],
  text, page_from, page_to, effective_from, effective_to, status, version_label,
  department, keywords[], retrieval_text, metadata{}`
- `passage`（检索片段 = 单元或单元的一段）
  `passage_id, unit_id, doc_id, text, position, token_count, metadata{}`
- `manifest`（发布清单）
  `release_id, created_at, documents[], counts{...,'units','passages'}, embedding{model,dim,prefix}, format_version`
- `active_release`：`{id, dir, created_at, ...manifest 摘要}`

`format_version` 用于将来迁移；读侧对未知字段宽容、对缺失字段给默认值。

## 5. 扩展点

| 想换什么 | 做什么 | 不碰什么 |
| --- | --- | --- |
| 向量库 | 在 `app/retrieval/backends/` 加实现，配置 `POLICYRAG_VECTOR_BACKEND` | 检索编排 |
| 生成模型 | 改 `.env` 的 base_url/model；或在 `app/llm/` 加客户端 | 提示词与编排 |
| 编码器 | 实现 `Encoder.encode`，配 `POLICYRAG_EMBEDDING_DIR` | 索引与融合 |
| 新文件格式 | 在 `app/ingest/parser.py` 注册扩展名 → 解析函数 | 结构化/发布 |
| 新领域 | 新增 `app/domain/<name>/` + 提示词 + 结构器配置 | 契约、检索、发布 |
| 新前端 | 只依赖 `/api/*` 与 NDJSON 事件 | 后端 |

## 6. 抽成独立框架的最小清单

把下面这些拷走即可得到一个与制度无关的「文档问答内核」：

```
app/core/contracts.py  app/core/text.py  app/settings.py  app/wiring.py
app/store/{catalog,releases}.py
app/retrieval/{encoder,lexical,query,engine,backends/*}
app/llm/{client,routing}.py
app/ingest/{parser,structure,quality,pipeline,publish}.py
app/qa/flow.py  app/api/*
```

需要同时删掉/替换的领域内容：`app/domain/versions.py`（换成目标领域规则）、
`app/llm/prompts.py` 里的制度口径、`knowledge/samples/` 样例、评测题库。
检查方法：`grep -rn "制度\|条款\|废止\|政策" app --include=*.py | grep -v app/domain`
应当只剩注释级引用。
