# 复用指南：把这个架构搬到下一个项目

> 适用场景：你有一个「一堆文档 + 要能问答 + 要能引用回原文」的新项目，
> 想直接复用 PolicyRAG 的内核，只替换领域知识。
> 目标架构见 [架构.md](架构.md)。

## 0. 先判断：真的要复用吗

满足下面任意两条，直接复用比从零写省 1–2 周：

- 文档是 PDF/DOCX/TXT，需要按章节/条款切分；
- 答案必须带出处（页码、条款号），不能只给一段话；
- 用户会问「现在还有效吗」「新版怎么规定」这类时效问题；
- 同一份文件会有多个版本，需要版本治理；
- 需要「不知道就说不知道」的拒答。

只需要向量检索 + 一段话回答、不要求引用的场景，用 LangChain 之类更省。

## 1. 拷什么

```
app/settings.py           配置对象（改默认值即可）
app/config.py             兼容门面（可保留）
app/core/contracts.py     部件契约
app/core/text.py          文本归一化
app/wiring.py             装配层（组合根，按发布加载）
app/store/catalog.py      元数据（文档/任务/发布/审计）
app/store/releases.py     发布目录与 active 指针
app/retrieval/            编码器、BM25、查询解析、检索引擎、向量后端
app/llm/client.py         OpenAI 兼容客户端（换模型只改 .env）
app/llm/routing.py        查询路由（寒暄/检索/闲聊）
app/ingest/               解析→结构化→质检→切分→发布
app/qa/flow.py            问答编排（事件流）
app/api/                   HTTP/SSE 适配
scripts/                  ingest / build_index / search / evaluate / smoke_test
```

**不要拷**：`app/domain/versions.py`、`app/llm/prompts.py` 的制度口径、
`knowledge/samples/`、`tests/eval/questions.jsonl`、`data/`、`models/`。

抽取后先做一次「空跑」验证：

```bash
python scripts/drill_extract.py     # 复制内核到 data/tmp/drill-*，用假模型跑通检索与问答
```

它打印 `DRILL OK` 才说明内核没有隐含依赖；换领域后也建议保留这个脚本当作烟测。

## 2. 换领域要动的五处

| 位置 | 改什么 | 例子 |
| --- | --- | --- |
| `app/domain/` | 新领域包：状态词、版本/时效规则、条款号解析 | 合同：草稿/生效/终止/续签 |
| `app/ingest/structure.py` | 结构识别规则（章节/条款/附件/表格） | 手册：步骤/注意事项 |
| `app/llm/prompts.py` | 系统提示词、拒答口径、引用格式 | 「依据《X》第 N 条」 |
| `app/ingest/quality.py` | 质检下限（页数、字符数、乱码率） | 扫描件占比高时调阈值 |
| 评测题库 | 30–50 题 + 判据 | 见 §5 |

## 3. 配置

复制 `.env.example` 为 `.env`，最小可用三行：

```
POLICYRAG_LLM_BASE_URL=https://<你的模型网关>/v1
POLICYRAG_LLM_MODEL=<模型名>
POLICYRAG_LLM_API_KEY=<key>
```

向量库默认 Chroma（纯本地、无 Docker）；`POLICYRAG_VECTOR_BACKEND=npz` 可退化为
零依赖的 npz 后端（适合小库、CI、无 chromadb 环境）。`POLICYRAG_DEVICE=auto`
会在有 CUDA 时用 GPU。

## 4. 上线前检查清单

1. `python scripts/ingest.py <文档目录>` 全量入库成功，`/api/documents` 条数正确；
2. `python scripts/build_index.py` 生成发布，`active_release.json` 指向新目录；
3. `python scripts/smoke_test.py` 13 项全过（健康检查、问答、引用、拒答、上传）；
4. `python scripts/evaluate.py --fail-under 0.8` 达到你的准确率门槛；
5. 抽 10 个真实问题人工核对：答案是否正确、引用是否指向原文、旧版是否被正确标注；
6. 前端只改品牌与配色，`/api/ask` 的 NDJSON 事件不要改。

## 5. 评测怎么做

- 题目按类型分组：精确（条款号/文号）、模糊（口语化）、多轮、跨文档、应拒答、更新后；
- 每类至少 4 题，总数 30–50；写进 `tests/eval/questions.jsonl`：
  `{"id","type","question","expect_keywords":[...],"expect_refuse":false}`；
- 判据不要绑死某一句话：用「必须出现的关键词 + 必须命中的文档」；
- 每次改检索/提示词/数据只重测受影响的题；`--full` 才跑全量。

## 6. 常见坑

1. **发布目录必须同版本**：units、passages、向量、manifest 四件套一起写，
   `active_release.json` 最后原子替换；否则会出现「向量是新库、单元是旧库」。
2. **不要把领域词写进通用层**：`app/retrieval` 里出现「制度」「废止」就是抽象泄漏，
   下次换领域会到处改。
3. **相关性闸门要可关**：小知识库上阈值过高会全是拒答，先设 0 跑通再调。
4. **表格与页图是引用质量的胜负手**：只给文字不给页码，用户不会信。
5. **事件协议是前端契约**：改事件名前先问前端；NDJSON 每行一个 JSON，别拼包。
6. **旧版本默认不进证据**：只在用户明确问旧版时给，并附「旧版仅作参考」提示。
